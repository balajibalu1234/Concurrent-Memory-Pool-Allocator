Architectural analysis

This project uses one pre-allocated buffer that is split into fixed-size chunks. The free chunks are tracked with a lock-free singly linked list. The head of that list is stored in an atomic pointer, so allocation and release can happen without using mutexes.

Concurrency safety

The allocator uses compare-and-swap to pop from the head on allocation and push back to the head on deallocation. I also added a small thread-local cache, so each thread can reuse recently freed chunks before it needs to touch the global free list. This reduces contention while keeping the core data structure lock-free.

Performance trade-offs

This design is well suited to repeated fixed-size requests because it avoids repeated calls to `malloc` and `free`. The allocator reuses its own internal storage, which makes it faster for workloads that repeatedly allocate and release the same sized blocks. It does not support variable-sized blocks, automatic growth, or chunk coalescing.

Memory safety audit

The pool allocates its backing storage once in the constructor and frees it once in the destructor. The free-list updates are protected by atomic operations, and the code uses aligned storage to reduce false sharing. For heavier workloads, a full production-grade design would still benefit from stronger ABA protection, such as hazard pointers or epoch-based reclamation.

Notes

This version stays intentionally simple for the assignment scope, but it now includes thread-local caching to reduce contention and better align with the requested concurrency design.
